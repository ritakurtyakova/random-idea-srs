# Процесс проектирования и нормализации базы данных

## 1. Исходная (денормализованная) структура

Для демонстрации проблем была рассмотрена условная таблица `Ideas_Flat`, содержащая все данные приложения «Генератор случайных идей»:

`Ideas_Flat (idea_id, content, genre_name, content_type, seed, favorite)`

В таблице хранятся текст идеи, название жанра, тип генерации, зерно генерации и информация об избранном.

**Проблемы исходной структуры:**

- **Избыточность:** названия жанров повторяются для разных идей.
- **Аномалия обновления:** при изменении названия жанра необходимо обновлять несколько записей.
- **Аномалия удаления:** при удалении последней идеи определённого жанра можно потерять информацию о самом жанре.

Для устранения этих проблем необходимо разделить данные на несколько связанных таблиц и провести нормализацию до третьей нормальной формы (3NF).

## 2. Первая нормальная форма (1NF)

Для приведения структуры к первой нормальной форме необходимо обеспечить атомарность значений в каждом поле.

В исходной структуре данные об идее, жанре и типе генерации хранились в одной таблице. Кроме того, одна генерация может возвращать несколько результатов. Если хранить все результаты в одном поле через запятую или другой разделитель, нарушается требование атомарности.

Для устранения этой проблемы данные разделяются на две таблицы:

- `Generation` — хранит информацию о процессе генерации: жанр, тип генерируемого содержимого, seed, уровень абсурдности и дату создания.
- `GeneratedIdea` — хранит отдельные результаты генерации. Каждая идея записывается в отдельную строку и связывается с генерацией через `generation_id`.

Таким образом, каждое поле содержит одно значение, а несколько результатов одной генерации представлены отдельными записями.

**Вывод:** структура приведена к первой нормальной форме (1NF), поскольку значения атрибутов атомарны, а повторяющиеся группы данных вынесены в отдельную таблицу.

## 3. Вторая нормальная форма (2NF)

Вторая нормальная форма требует, чтобы таблица уже находилась в первой нормальной форме и каждый неключевой атрибут полностью зависел от первичного ключа.

В проектируемой базе данных таблицы `Genre`, `Generation`, `GeneratedIdea`, `Favorite` и `AppSettings` используют простые первичные ключи. Поэтому частичные зависимости от составного первичного ключа отсутствуют.

Дополнительно информация о жанрах вынесена в отдельную таблицу `Genre`:

- `Genre` хранит идентификатор и название жанра, а также его описание.
- `Generation` содержит поле `genre_id`, которое ссылается на `Genre`.

Это позволяет не повторять название и описание жанра в каждой записи генерации.

**Вывод:** структура соответствует второй нормальной форме (2NF): частичные зависимости отсутствуют, а сведения о жанрах хранятся отдельно от данных генераций.

## 4. Третья нормальная форма (3NF)

Третья нормальная форма требует, чтобы таблица находилась во второй нормальной форме и не содержала транзитивных зависимостей неключевых атрибутов от первичного ключа.

В проектируемой базе данных сведения о жанрах вынесены в самостоятельную таблицу `Genre`.

Таблица `Generation` содержит только внешний ключ `genre_id`, который ссылается на соответствующую запись в `Genre`. Название и описание жанра не хранятся непосредственно в таблице генераций.

Таким образом, информация о жанре зависит от первичного ключа таблицы `Genre`, а не от записи генерации.

Аналогично избранные идеи хранятся в отдельной таблице `Favorite`, связанной с `GeneratedIdea` через внешний ключ `idea_id`.

**Вывод:** структура спроектирована с учётом требований третьей нормальной формы (3NF): сведения о жанрах и избранном вынесены в отдельные таблицы, что уменьшает дублирование данных и предотвращает аномалии обновления.

## 5. Анализ связей многие-ко-многим (M:N)

При проектировании базы данных были рассмотрены связи между основными сущностями приложения.

В текущей модели связи M:N не требуются:

- Один жанр может использоваться во многих генерациях, но каждая генерация ссылается не более чем на один жанр.
- Одна генерация может содержать несколько результатов, но каждый результат относится к одной генерации.
- Каждая запись избранного относится к одной идее, а ограничение уникальности `idea_id` не позволяет сохранить одну идею повторно.

Таким образом, связи реализуются с помощью внешних ключей без дополнительных промежуточных таблиц.

**Вывод:** в рамках текущих требований приложения отдельная таблица для реализации связи M:N не нужна. Если в будущем появится возможность назначать одной идее несколько жанров или категорий, потребуется добавить соответствующую таблицу-связку.

## 6. Финальная схема базы данных

После анализа требований и нормализации до третьей нормальной формы (3NF) итоговая модель включает пять таблиц.

### 6.1. Состав таблиц

1. **Genre** — хранит доступные жанры: идентификатор, название и описание.
2. **Generation** — хранит параметры генерации: жанр, тип содержимого, seed, уровень абсурдности, дополнительные параметры и дату создания.
3. **GeneratedIdea** — хранит результаты генерации. Каждая запись соответствует одной идее и связана с конкретной генерацией.
4. **Favorite** — хранит информацию о сохранённых пользователем идеях и дату сохранения.
5. **AppSettings** — хранит последние настройки приложения: выбранный жанр, тип содержимого, seed и уровень абсурдности.

### 6.2. Связи между таблицами

- `Genre (1) — (N) Generation`: один жанр может использоваться во многих генерациях.
- `Generation (1) — (N) GeneratedIdea`: одна генерация может создавать несколько идей.
- `GeneratedIdea (1) — (0..1) Favorite`: идея может отсутствовать в избранном или иметь одну запись в избранном.
- `Genre (1) — (0..N) AppSettings`: настройки могут ссылаться на жанр; таблица настроек ограничена одной записью.

### 6.3. Принципы целостности данных

- Для каждой таблицы определён первичный ключ.
- Связи между таблицами реализованы внешними ключами.
- Для названий жанров предусмотрено ограничение уникальности.
- Для `Favorite.idea_id` предусмотрено ограничение уникальности, предотвращающее повторное сохранение одной идеи.
- Для уровня абсурдности предусмотрена проверка допустимого диапазона значений от 0 до 100.

### 6.4. Итог

Итоговая структура разделяет данные по назначению, уменьшает дублирование и обеспечивает ссылочную целостность. Модель соответствует требованиям первой, второй и третьей нормальных форм (1NF, 2NF и 3NF) в рамках принятых проектных решений.
